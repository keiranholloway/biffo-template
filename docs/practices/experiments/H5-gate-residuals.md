# H5 — the four residual gate gaps, ranked by measured ROI, and one of them is not worth fixing

**Status:** `running`
**Pre-registered:** 2026-07-29, **before** any of the four is built
**Review on:** 2026-08-05 (7 days — the estate's review cadence)

> Written and committed before the intervention, like H1–H4. A prediction
> written afterwards is a description, and it will always fit.

---

## Why there is an H5

[H4](./H4-shift-left-gates.md) took gate coverage from 45% to 100% and arming
from 18% to 100%. Its capture left **four named gaps**, and the honest thing to
do with four items on a list is not to build all four — it is to price them
first and then decline the ones that do not pay.

That is the whole point of this page. **One of the four turns out to be worth
nothing, and the measurement is what shows it.** Recording a declined fix with
its number is more useful than shipping it, because the next person to notice
the same gap will otherwise re-propose it.

## The unit: what a round trip costs

Everything below is priced in **CI round trips**, measured 2026-07-29 from
GitHub Actions run durations (`run_started_at` → `updated_at`, p50 over the last
50 CI runs per repo):

| repo class | CI p50 | discover + confirm (2 runs) |
| --- | ---: | ---: |
| `biffo-template` | 2.4 min | **5 min** |
| siblings (`tabsii-crm`) | 7.0 min | **14 min** |
| instances (`tabsii-platform`) | 8.4 min | **17 min** |

A defect the gate catches locally costs seconds. The same defect reaching CI
costs one round trip to discover and another to confirm the fix — plus the merge
race re-entry, which is not counted here, so every figure below is an
**underestimate of the saving**.

## Gap 1 — a PR cannot tell it is carrying a stale shared file

**Measured.** Drift is detectable only by running `shared-sync.sh --check`
against a fresh template clone. The daily cron now runs it (#867), which caps
staleness at 24h — but a PR merged inside that window still ships against a
stale gate, and nothing in the PR says so.

The observed incident: `tabsii-crm` ran a **two-version-old** gate and reported
`verify passed` on a 700-line TypeScript-and-Python change. Running `tsc` by
hand afterwards found **three real type errors**, every one of which would have
been a CI failure.

**ROI:** 3 avoided CI failures × 14 min = **~42 min in a single PR**, and that
is the near-miss rather than the loss — the errors were caught by an agent
choosing to run `tsc` manually. Frequency: every shared-file change opens a
window, and there were **six** on 2026-07-29 alone.

**Intervention:** stamp the template's core version into `verify.sh` at sync
time, and have the gate print it. A repo's gate then states which template it
came from, and CI can assert it matches.

**Verdict: build.** Highest measured cost of the four.

## Gap 2 — `commit-msg` is inert in every sibling

**Measured, and this is the one that does not pay.** Non-conventional commit
subjects over 30 days, `--no-merges`:

| repo | commit-msg hook | non-conventional |
| --- | --- | ---: |
| tabsii-crm | **none** | **0 / 96** |
| tabsii-intake | **none** | **0 / 16** |
| tabsii-geo | **none** | **0 / 21** |
| tabsii-marketplace | **none** | **0 / 13** |
| tabsii-app | **none** | **0 / 6** |
| biffo-platform-app | **none** | **0 / 13** |
| | | **0 / 165** |

**Zero violations in 165 commits across six repos with no hook at all.**

The control looks worse, and does not survive inspection: `tabsii-platform` 24/292
and `biffo-platform` 10/97 are **almost entirely `Upgrade Biffo core X → Y`** —
squash subjects generated by `biffo core upgrade`'s own PR title. Those are
tolerated by design: the `release-subject` guard only requires a conventional
subject where a change cuts a core release, and an instance never does.

Two things were nearly reported as findings here and were not:

1. A first pass measured 12% in `tabsii-platform` using a regex that rejected
   `feat(db,api):` — commas are legal in a scope. The tool was wrong, not the
   repo.
2. `release-subject` looked like a fail-open (`No base ref…`) until its exit code
   was read properly: it exits **2**, loudly, when it cannot run.

**ROI: ~0.** Expected saving is zero incidents, because the measured rate is
zero. Cost to build: a commitlint config and dependency in six repos, plus a new
failure mode in each.

**Verdict: declined, with the number.** Re-open if the rate rises above zero —
the daily corpus makes that visible without anyone watching for it.

## Gap 3 — the exclusion list is written by hand, and one entry was wrong

**Measured.** Eight exclusions in `verify-parity.test.ts`. **One was false** —
`bandit`'s rationale claimed *"the finding gate is the upload step, not the
run"*, when `bandit -ll` exits non-zero on findings and it is the run step that
fails. It stood for **~14 days** and cost at least one observed CI round trip
(tabsii-platform PR #313, job 90502765804) at instance prices: **~17 min**.

Base rate: **1 wrong entry per 8, per fortnight.** The list grows as CI grows.

**Intervention:** assert each exclusion mechanically rather than in prose —
either the check genuinely cannot run locally (network, needs a PR, needs
history), or it is slow, and the slow ones must carry a *measured* duration
rather than an adjective.

**ROI:** one prevented recurrence per ~8 exclusions ≈ **17 min per fortnight**,
rising with the size of the list. Modest, but the failure mode is the expensive
kind: a wrong exclusion is invisible and silently removes a check.

**Verdict: build.**

## Gap 4 — `pytest` is opt-in and nothing prompts the fast suites to opt in

**Measured.** `uv run pytest -q --no-cov`, wall clock, 2026-07-29:

| repo | pytest | in the gate? |
| --- | ---: | --- |
| tabsii-marketplace | **1.7s** | no |
| tabsii-geo | **2.1s** | no |
| tabsii-intake | **2.5s** | no |
| tabsii-crm | **2.7s** | no |
| biffo-template | 51.2s | correctly excluded |
| biffo-platform | 57.4s | correctly excluded |
| tabsii-platform | 85.6s | correctly excluded |

The exclusion is right for the three repos it was written against and wrong for
the four it was applied to. **The fastest suites in the estate are the ones not
being run.**

**ROI, explicitly:**

- Cost: **2.5s** added to every push in a sibling.
- Saving: **14 min** per Python test failure kept out of CI.
- **Break-even: one catch per 336 pushes.**
- Observed rate: roughly **one sibling pytest failure per 165 commits** over the
  last 30 days — about **twice the rate needed** to pay for itself.

**Intervention:** include `pytest` automatically where it runs under a
threshold, rather than requiring an opt-in nobody issues. `BIFFO_VERIFY_PYTEST`
stays as an override in both directions.

**Verdict: build.** Best ratio of the four, and the cheapest to implement.

## Prediction

By **2026-08-05**, over a 7-day window:

- **Gate coverage stays at 100%** in every repo with CI — primary. The three
  interventions must not reduce it, and gap 4 raises the denominator, so this is
  a genuine constraint rather than a restatement.
- **Zero PRs merge against a stale shared gate.** Gap 1's stamp makes this
  observable; today it is not.
- **`pytest` runs in all four fast siblings** and the gate's p50 duration in
  those repos stays **under 45s**.
- **Every exclusion carries a mechanical justification**, and the count of
  prose-only rationales is **zero**.

## What is measured daily, and what is not (#914)

- **Gate coverage** — H5's primary — is audited every morning by
  `scripts/gate-coverage.sh` and lands in `docs/practices/data/estate-audits.json`
  as a pass/fail plus a prose summary. On 2026-07-30 it read **`ok: false`**
  ("some gates do not cover their own CI"), i.e. the primary prediction is
  currently failing, six days before review. The audit does not yet emit
  per-repo *numbers*, so which repo and which kind still needs reading by eye.
- **The locally-catchable share** (H4's primary, and the thing these four gaps
  are meant to move) is collected daily since #914 — see
  `docs/practices/metrics.md#gates`.
- **Gate duration p50 and bypass rate are not measured at all.** Both need
  `verify.sh` to persist a run log; it prints per-check durations and keeps none.
  Since gate duration in siblings above 60s refutes H5 on its own, **this
  experiment cannot currently be refuted by its primary counter-metric** — worth
  stating plainly at review rather than reporting the coverage number alone.

## Counter-metric — the entire risk

Three of these add work to every push. The risk is the same one H4 named:
**friction that gets routed around**.

- **Gate duration p50 in siblings above 60s refutes H5**, whatever the coverage
  says. Currently ~20s; gap 4 adds ~2.5s and gap 1 adds a string comparison.
- **Bypass rate above 10%** (`BIFFO_SKIP_VERIFY` plus `--no-verify`) refutes it.
- **A gate that blocks a push CI would have passed** — the "stricter than CI"
  defect patched three times on 2026-07-29 — recurring even once refutes the
  claim that deriving from `ci.yml` fixed the class.

## Falsification

**Refuted** if gate coverage drops below 100% in any repo with CI, or if any
counter-metric breaches.

**Gap 2 is refuted as a decision** — i.e. it should have been built — if the
non-conventional rate in the six hook-less repos rises above **2%** in the
window. It is 0% now; that is the number to beat.

**Inconclusive** if fewer than 20 pushes occur in sibling repos in the window,
which would leave gap 4's break-even untestable.

**Most likely reason for refutation, stated in advance:** gap 1. A version stamp
is easy to write and easy to make meaningless — if the stamp is generated from
the wrong side (the receiving repo rather than the template), it will always
match and will report perfect health forever. That is precisely the shape of
every instrument defect on 2026-07-29, and it is the one to test adversarially
rather than trust.

## Cost and reversibility

Hours to build, seconds per push to run. Fully reversible — each is an
independent change to `verify.sh` or its parity test, and CI runs every check
regardless, so a refuted H5 costs only the time spent.

## Confounds acknowledged in advance

- **n=1 per gap.** Gap 1 rests on one observed incident, gap 3 on one wrong
  exclusion. The ROI figures are therefore point estimates from single events,
  not rates — say so when reporting.
- **The round-trip prices are p50s from 50 runs per repo**, taken on a day when
  the estate was unusually busy. They will be lower on a quiet week, which makes
  every saving above an overestimate in that direction.
- **Gap 2's zero is over 30 days of largely agent-authored commits.** Agents
  follow the convention because it is in `AGENTS.md`; a human-heavy month could
  produce a different number, and the falsification threshold is set at 2% for
  exactly that reason.
- **Gap 4's observed failure rate (~1 per 165) is one event.** It is the right
  order of magnitude and no more; the break-even figure is the robust part.
